# 軽量マークアップ文書作成アプリ 要件定義書

**バージョン：** 0.2（初期検討反映版）  
**作成日：** 2026年10月16日  
**プロジェクト名：** 未定（仮：Typer）  
**開発形態：** 個人開発・AI支援開発

---

## 1. プロジェクト概要

### 1.1 目的

Markdownの簡潔な記述方法を基本としながら、表の列幅、文字装飾、行間、ページ設定などを柔軟に制御できる、軽量なデスクトップ文書作成アプリケーションを開発する。

主な用途は、企業内で使用する簡易的な報告書や業務文書の作成とする。

Microsoft Wordのような高機能ワープロの完全な代替ではなく、**テキストを中心とした簡潔な操作で、体裁の整った文書を効率よく作成できること**を目指す。

### 1.2 基本コンセプト

- **あくまでも書き味はMarkdown的であること**を維持する。
- MarkdownとHTMLの中間程度の、業務文書に必要十分な書式制御能力（特に表の列幅や行間など）を持たせる。
- 文書作成時の煩雑な書式操作を減らす。
- 用紙サイズや改ページを考慮した組版に対応する。
- 正式な成果物はPDF形式で出力する。
- HTML形式ではページ概念に依存しない連続表示を実現する。
- **可能な限り単一実行ファイル（ポータブルな1つの `.exe`）で動作・配布できること**を目指す。
- 起動速度、入力応答性、メモリ消費を重視する。
- 不必要な機能を増やさず、シンプルな操作体系を維持する。

### 1.3 想定する文書

- 社内報告書
- 業務改善報告書
- 作業結果報告書
- 簡易的な技術文書
- 議事録
- 業務手順書

主に数ページ程度の文書を想定する。ただし、具体的な最大ページ数は性能検証後に決定する。

## 2. システム要件

### 2.1 アプリケーション形式

| 項目 | 要件 |
|---|---|
| アプリケーション | デスクトップアプリ |
| 対象OS | Windowsを第一候補 |
| 配布・実行形態 | **原則として外部ランタイム不要の単一EXEファイル（ポータブル実行形式）** |
| 動作方式 | 原則ローカル実行 |
| ネットワーク | 基本機能はオフライン利用可能とする |
| 入力方式 | テキストエディタ形式 |
| 保存形式 | 独自Markdown拡張形式（基本はプレーンテキスト／`.md` 互換） |
| 主出力 | PDF |
| 副出力 | HTML |
| 開発言語 | Rust（第一候補） / C++（代替候補） |
| UI候補 | **egui（仮採用・第一候補）** / **Slint（比較候補）** / Qt（代替候補） |
| 組版エンジン | Typst（ライブラリとしてバイナリ内に直接組み込み） |

### 2.2 設計方針

アプリケーションを以下の構成要素に分離する。

1. テキスト編集機能（UI層）
2. マークアップ構文解析（Parser層）
3. **内部文書モデル（AST / 拡張属性用の器を持つ中間表現）**
4. PDF向けページ組版処理（Typst変換・組版層）
5. プレビュー描画処理（組版結果のラスタライズ／SVG描画層）
6. PDF出力処理
7. HTML出力処理

**重要方針：**
- 構文解析、内部文書モデル、描画、UIを疎結合にし、UIフレームワークの差し替え（egui ⇄ Slintの比較等）や将来的な構文変更に対応しやすい構成とする。
- **最初からすべての独自構文を固定せず、まずは「拡張属性用の器（オプションフィールド）」を備えた内部文書モデルを作り、標準Markdownで一気通貫に描画・PDF出力できる土台を構築した上で、実際の文書作成を通じて独自構文の記法を調整・追加していく。**

## 3. 独自マークアップ言語の要件

### 3.1 基本方針

標準Markdown（CommonMark + GFMテーブル等）を基本構文とし、表の制御や行間・文字装飾など、標準Markdownでは手が届かない部分のみ独自の書式指定構文を追加する。

既存Markdownとの互換性を可能な範囲で維持し、拡張構文を使用しない場合は一般的なMarkdownとしてそのまま記述・閲覧できることを目標とする。

### 3.2 基本Markdown機能

以下の標準機能に対応する。

- 見出し（`#` 〜 `######`）
- 段落・改行
- 太字・斜体・打ち消し線
- 箇条書き・番号付きリスト
- 表（GFMパイプテーブル）
- 引用（`>`）
- 水平線（`---`）
- リンク・画像
- コードブロック・インラインコード

### 3.3 独自拡張機能（段階的に導入）

| 機能 | 内容 | 優先度 |
|---|---|---|
| 表の列幅 | 各列の幅を比率・固定値・自動などで指定 | 必須 |
| 行間 | 文書全体または段落単位で設定 | 必須 |
| 文字色 | 文章の一部分のみ色を変更 | 必須 |
| ページ設定 | 用紙サイズ・余白・方向 | 必須 |
| 文字サイズ | 文書全体・部分的な変更 | 高 |
| 文字配置 | 左寄せ・中央寄せ・右寄せ | 高 |
| 段落間隔 | 段落前後の余白設定 | 高 |
| 表の配置 | 表全体・セル内の文字配置 | 高 |
| 任意改ページ | 指定箇所から次ページへ送る | 高 |
| 改ページ抑制 | 見出しや表などの分割制御 | 高 |
| セル結合 | 表の行・列の結合 | 将来検討 |
| スタイルプリセット | 定型的な書式を再利用 | 将来検討 |

### 3.4 構文の設計案（プロトタイプ検証時に最終決定）

以下は仮の構文であり、基本Markdown描画の実装後に使用感を検証しながら正式決定する。

**表の列幅（表の直前に記述するブロック属性案）**
```markdown
{widths: 20%, 50%, 30%}
| 項目 | 内容 | 備考 |
| :--- | :--- | :---: |
| 発生日時 | 2026年10月16日 | 監視ログより検知 |
```

**段落属性（行間・文字配置など）**
```markdown
{align: right}
2026年10月16日

{line-height: 1.2}
この段落のみ行間を詰めて表示する。
```

**部分文字装飾（表のパイプ `|` と衝突しない記法案）**
- 案A（ブラケット＋属性）：`[重要事項]{red}` または `[重要事項]{color: red}`
- 案B（コロン区切り）：`{red: 重要事項}`
- 案C（従来案・要エスケープ検討）：`{color:red|重要事項}`

**改ページ**
```markdown
:::pagebreak
```
（または `{pagebreak}`）

**文書全体設定（YAML Frontmatter形式）**
```yaml
---
paper: A4
orientation: portrait
margin: 20mm
font-size: 10.5pt
line-height: 1.5
---
```

### 3.5 構文設計上の検討事項

- 表（`|` 区切り）のセル内で文字装飾を使った際に構文衝突しない記号体系
- ブロック属性（直後の要素に適用）とインライン属性（部分文字列に適用）の明確な区別
- 入れ子構造への対応と特殊文字のエスケープ
- 構文エラー発生時でもクラッシュせず、プレーンテキストとして安全にフォールバックする挙動
- 単位の取り扱い（`pt`, `mm`, `%`, `auto` など）

## 4. 文書レイアウト・ページ組版要件

### 4.1 ページの基本動作

内部文書モデルでは、文書を見出し、段落、表などの連続した構造として管理する。  
PDF出力およびプレビュー時には、指定された用紙設定に基づき、Typstエンジンを通じて自動的にページへ分割する。

### 4.2 ページ設定

初期仕様では以下を対象とする。

- A4縦向き（portrait）
- A4横向き（landscape）
- 上下左右の余白設定
- 自動改ページおよび手動改ページ

### 4.3 組版上の要件

- 日本語の適切な文字折り返し・禁則処理
- 文字サイズ・行間の反映
- 表の列幅設定およびセル内での自動折り返し
- 見出し直後の不自然な改ページの抑制（orphan/widow制御）
- ページ境界における段落・表の分割制御（複数ページにまたがる表のヘッダ繰り返し等）
- フォントの埋め込みを含むPDF表示互換性への配慮

高度な組版機能はTypstの機能を活用し、原則として独自実装しない。

## 5. エディタ・プレビュー機能

### 5.1 編集方式

基本はテキストエディタ方式とする。  
WYSIWYG型ワープロを目指すのではなく、Markdown風のテキスト入力を中心とする（左ペイン：エディタ、右ペイン：ページプレビューの2ペイン構成を基本とする）。

### 5.2 基本編集機能

- テキスト入力・編集（適切な日本語IMEインライン変換対応）
- ファイルの新規作成・読み込み・上書き保存・名前を付けて保存
- 元に戻す（Undo）・やり直し（Redo）
- コピー・切り取り・貼り付け
- 検索・置換（段階的に実装）
- 構文ハイライト（段階的に実装）

### 5.3 プレビュー機能

文書をページ単位で表示するプレビューを用意する。

- PDF出力と一致するページ表示（Typst組版結果のレンダリング）
- 用紙サイズ・余白・文字装飾・表の反映
- 複数ページのスクロール閲覧・ズーム操作
- 編集内容に応じたリアルタイム／準リアルタイム更新

### 5.4 プレビュー処理方針

- キー入力ごとにPDFファイル全体を生成・ディスク書き出ししない（メモリ上で完結させる）。
- 入力操作（UIスレッド）と組版処理（ワーカースレッド等）を分離し、デバウンス（入力停止後数百msでの更新）を取り入れる。
- Typstのインクリメンタルコンパイル・キャッシュ機構を活用する。
- 編集中のテキスト入力応答性を最優先する。

## 6. 出力機能

### 6.1 PDF出力（必須）

正式な報告書の提出・配布・印刷を目的とする。

- 用紙サイズと余白の反映、正確なページ分割
- 日本語フォントの埋め込みと正確な表示
- 表・書式の再現
- 標準的なPDFビューアで閲覧可能、完全オフラインで生成可能

### 6.2 HTML出力（必須・Phase 3にて実装）

ブラウザ上で読みやすい、連続した文書の生成を目的とする。

- ページ境界に依存しない連続表示、画面幅に応じたレスポンシブなレイアウト
- 見出し・段落・表・文字装飾・行間のCSSによる反映
- 単一HTMLファイル（CSS内包）として外部サービスなしで閲覧可能な出力
- PDF専用の改ページ指定などは、HTML出力時に原則無視（または区切り線等で代替）する。

## 7. 非機能要件

### 7.1 配布形態・ポータビリティ

- **単一実行ファイル（Single `.exe`）**：インストール作業や管理者権限を不要とし、実行ファイル1つを配置するだけで動作することを原則とする。
- 必要な静的リソース（アイコン、デフォルトスタイルテンプレート等）はバイナリ内に埋め込む。

### 7.2 性能・軽量化方針

- 起動時間、待機時メモリ消費、編集時の入力応答時間、プレビュー更新時間、配布サイズを重視する。
- 不要な常駐処理や外部プロセス起動を行わない（Typstも外部CLI呼び出しではなくライブラリとしてプロセス内実行する）。
- 組版中もエディタのキー入力をブロックしない。

### 7.3 安定性・保守性・日本語対応

- 記述途中の不完全なマークアップによってアプリが異常終了しない。
- 文書モデル・組版コアとUIフレームワークを分離し、自動テストを可能にする。
- 日本語環境（Windowsシステムフォントの活用または日本語フォントの適切なフォールバック、全角・半角混在、禁則処理）を第一に考慮する。

## 8. 技術構成

### 8.1 採用スタック（第一候補）

| 領域 | 技術候補 | 備考 |
|---|---|---|
| 開発言語 | **Rust** | 単一EXE化、高速性、メモリ安全性、Typstとの直接統合に最適 |
| UIフレームワーク | **egui (`eframe`)** *(仮採用)* | 純Rust製、単一バイナリ化が容易、軽量、即座にプロトタイプ構築可能 |
| UI比較候補 | **Slint** | ネイティブ感や宣言的UIの比較対象として、コア分離設計により差し替え可能にしておく |
| Markdown解析 | **`pulldown-cmark` + 前処理/拡張** | Rust標準の高速CommonMark/GFMパーサーをベースに独自属性を解釈 |
| 内部文書モデル | **Rust独自AST構造体** | 拡張属性（列幅・行間・色など）のOptionalフィールドを持つ中間モデル |
| ページ組版・PDF生成 | **`typst` / `typst-pdf`** | 外部プロセスではなくRustクレートとして直接リンク |
| プレビュー描画 | **`typst-render` (または `typst-svg`)** | メモリ上で各ページを画像（またはSVG）化し、`egui` のテクスチャとして高速描画 |
| HTML生成 | **内部文書モデルからの直接出力** | ASTからクリーンなHTML+CSSを生成 |

## 9. 段階的開発アプローチ（マイルストーン概要）

最初からすべての拡張構文を固定せず、**「まず標準Markdownで動く単一EXEアプリを作り、実際に動かしながら拡張記法を設計・追加する」** アプローチをとる。

1. **Step 1：コアパイプライン＋最小GUIの貫通（標準Markdown版）**
   - 拡張用の「器」だけ持たせた内部文書モデルを定義。
   - 標準Markdown（見出し・段落・リスト・表）を `egui` エディタで入力し、リアルタイムにTypstでプレビュー表示＆PDF出力できる単一EXEを作成する。
   - 日本語フォントの読み込みと日本語IMEの入力感を最優先で検証する。
2. **Step 2：独自拡張機能（表の列幅・行間・文字色・ページ設定）の設計と実装**
   - Step 1のアプリで実際の業務文書サンプルを書きながら、最も書きやすい拡張構文を決定・実装する。
3. **Step 3：エディタとしての実用性向上とHTML出力**
   - ファイル操作（開く・保存・未保存警告）、Undo/Redo、構文ハイライト、改ページ制御、HTML出力機能を追加する。
4. **Step 4：品質向上・性能最適化・パッケージング**
   - 非同期プレビュー更新（デバウンス・ワーカースレッド化）、エラーハンドリング、単一EXEのファイルサイズ・メモリ最適化を行う。

*(※具体的な実装ステップの詳細は別紙 `roadmap.md` を参照)*

## 10. 初期段階で対象外とする機能

開発規模と動作の軽量性を維持するため、以下は初期仕様の対象外とする。

- Word形式（DOCX）の入出力 / PowerPoint形式の出力
- 完全なWYSIWYG編集
- 複雑な図形描画機能
- クラウド共同編集 / リアルタイム複数人編集
- マクロ・スクリプト実行機能 / データベース連携
- 高度なテンプレート管理 / Wordと同等の組版機能

> **補足（スコープの見直し）**：上記のうちWord（DOCX）については、開発を進める中で需要が確認されたため、**一方向の出力（.docxへのエクスポート）のみ**実装済み（入力・読み込みは引き続き対象外）。詳細は [docs/MANUAL.md](MANUAL.md) の「出力（PDF / HTML / Word）」章を参照。他の対象外機能（WYSIWYG、クラウド共同編集等）は変更なし。

## 12. プロジェクトの基本原則

- **原則1：文章を書くことを中心にする。**（自然なテキスト記述で文書を作成できるようにする）
- **原則2：装飾機能は必要十分にとどめる。**（一般的な社内文書に必要な書式制御を優先し、簡潔さを重視する）
- **原則3：原稿と出力形式を分離する。**（内部文書モデルを介し、PDFとHTMLをそれぞれの用途に適した形で生成する）
- **原則4：既存の組版技術を活用する。**（Typstの組版能力を最大限に活かし、車輪の再発明を避ける）
- **原則5：軽快さとポータビリティを損なわない。**（単一EXEの手軽さ、起動速度、入力応答性を常に維持する）
- **原則6：動くものを作りながら段階的に育てる。**（まず基本Markdownで動く土台を作り、実運用に即して拡張構文を磨く）
